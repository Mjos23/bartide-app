# Nearby restaurant ordering

Customers open `/restaurants` (also `/nearby`), request browser location access, and optionally filter by restaurant name. Results are ordered by unrounded straight-line distance in miles. Slug order stabilizes exactly equal distances; availability, fees and popularity do not change ranking. Pages contain up to 50 results. Order links open the existing `/order/{slug}` checkout, which remains authoritative for prices, payment methods, delivery ZIP coverage and availability.

Restaurant owners/managers open Menu and settings, then **Help nearby customers find you**. Enter the public street address, capture the restaurant position while physically there or enter its map coordinates, verify the map, enable listing and save. Listings are opt-in. Only active BarTide restaurants with enabled ordering configuration, valid menus and pickup or delivery appear. Paused restaurants retain their distance position and display that ordering is paused. Drafts, other business types, disabled configurations, unlisted restaurants, invalid positions and malformed menus are excluded.

Directory settings live in `bartide_customers.menu_json.venue.directory`; this release requires no database migration. The existing menu editor's authorization, version checking, form origin validation and antiforgery protection apply. Old profile saves preserve directory settings. Unlisting is immediate.

`POST /api/v1/restaurants/nearby` accepts latitude, longitude, optional name search and offset. Coordinates must be finite and within geographic bounds. Guest coordinates are neither persisted nor included in URLs; the response is uncached and the endpoint uses the existing ordering rate limit. Browser location is requested only after an explicit click. Denied or unavailable location gives retry guidance; direct restaurant menu links remain usable. This version uses device location rather than address geocoding, and distances are not driving distances. Restaurant search scans active venue records; if the directory grows substantially, add a spatial index without changing distance-only ranking.

Drivers use the existing `/driver/signin` account entry and `/driver` profile/offer workspace. Joining or listing a driver profile grants no access to restaurant orders. Each restaurant owner/manager offers work, the driver explicitly accepts, and active tenant-specific hiring and membership are required for assignments. Existing in-house teams remain supported. Ending a hire removes access; reactivating a membership alone cannot bypass that restriction. Payment and payout settings are unchanged.

Verification: `scripts/verify-restaurant-discovery.py` exercises real local API/web/database behavior, ranking, filtering, pagination, direct orders, ownership, stale versions and form protections. `scripts/verify-restaurant-location.cjs` checks explicit browser requests and location failures with synthetic coordinates. `scripts/verify-driver-network.py` exercises the existing hiring/assignment isolation rules. All fixtures are synthetic and do not contact production identity, payment or location providers.
